# 安全密码管家 — 架构决策记录（ADR）

> **目的**：把研发过程中「有取舍、需正反权衡」的决策**显式化**，防止团队凭感觉反复横跳。每个 ADR 记录：背景 / 决策 / 正反权衡 / 结论 / 可选后续。
> **编号规范**：ADR-###，新决策追加，**不删除历史决策**（可标记 `superseded`）。

---

## ADR-001｜跨端技术选型：Flutter + 安全逻辑原生 vs. 全原生

| 项 | 内容 |
| :-- | :-- |
| 背景 | 需覆盖 Android/iOS，含 Keystore/Keychain、AutoFill、Accessibility、FLAG_SECURE 等系统深度集成 |
| 决策 | **UI 用 Flutter；安全关键（加密、密钥访问、生物识别、平台防护）用 Kotlin/Swift 原生，经 method-channel 桥接** |
| 权衡 | ✅ 跨端 UI 效率高、一致性高；✅ 密码学走成熟原生库，避免纯 Dart 实现安全风险；❌ 桥接增加复杂度、存在跨端边缘 bug 风险 |
| 结论 | **采纳**。安全不承担跨端抽象风险，UI 共享是可信收益 |
| 后续 | 桥接口需单测 + 分层契约（见 `01` 架构规格 §5）；预留 Web 端可行性评估 |

## ADR-002｜密钥体系：KEK/DEK 分层 vs. 单主密钥直接加密

| 项 | 内容 |
| :-- | :-- |
| 背景 | 主密码修改频率 vs 全量数据重加密成本 |
| 决策 | **KEK(主密码派生) → 包 DEK → DEK 加密全量数据** |
| 权衡 | ✅ 改主密码只需重包 DEK，不重加密全量（性能好）；✅ 支持 RecoveryKey 解包、字段级 FDEK；❌ 增加包裹格式与版本管理 |
| 结论 | **采纳**（PRD V2.0 §2.1 已定） |
| 后续 | 包裹带 `version + kdf 参数`，保证跨版本向上兼容 |

## ADR-003｜高敏感字段加密：UI 拦截 vs. 字段级加密（FDEK）

| 项 | 内容 |
| :-- | :-- |
| 背景 | 仅 UI 拦截二次验证，攻击者可能直接读库/读内存绕过 |
| 决策 | **高敏感字段用 FDEK 独立加密；未二次验证前密文在库中即不可解密（真字段级权限）**，UI 拦截作为第二道 |
| 权衡 | ✅ 纵深防御，绕 UI 也无法取明；✅ 列表可用 `masked_preview` 脱敏显示；❌ 实现复杂度上升、需管理 FDEK 生命周期 |
| 结论 | **采纳**（Phase 2 起，T2.2） |
| 后续 | FDEK 存储与 DEK 同层次安全；支持 FDEK 轮换 |

## ADR-004｜恢复方案：三通道 + 两把钥匙原则

| 项 | 内容 |
| :-- | :-- |
| 背景 | V1.0 无恢复机制，主密码遗忘即丢数据；V2.0 须「可恢复但不泄密」 |
| 决策 | **密码提示词(本地) + 本地恢复码(RecoveryKey) + 邮箱/短信验证(两把钥匙：验证码 + RecoveryKey)** |
| 权衡 | ✅ 覆盖不同用户风险偏好；✅ 验证码与恢复码分离，单一泄露无效；✅ 服务端零知识；❌ 恢复码需用户离线保管，教育成本 |
| 结论 | **采纳**（PRD §2.2，验收 8.2） |
| 后续 | 首次初始化强提示备份 RecoveryKey；提供打印/导出恢复码；评估「紧急联系人」扩展 |

## ADR-005｜云恢复的零知识边界：服务端存什么

| 项 | 内容 |
| :-- | :-- |
| 背景 | 绑定邮箱/手机找回需要服务端参与，但不得破坏零知识 |
| 决策 | **服务端只存 `contact_hash`(不可逆) + `recoverywrap_remote`(密文)；不存主密码/KEK/RecoveryKey/明文；解密只在客户端** |
| 权衡 | ✅ 服务端被攻破也无明文；✅ 满足 PIPL 最小留存；❌ 无恢复码则服务端无法帮用户重置（刻意保持） |
| 结论 | **采纳**（见 `04` API 契约 §2） |
| 后续 | 服务端实现需通过 `TC-CRY-06`（日志/存储无明文密钥）验收 |

## ADR-006｜剪贴板策略：高敏感字段默认不写系统剪贴板

| 项 | 内容 |
| :-- | :-- |
| 背景 | 剪贴板是系统级共享通道，且 OEM 有剪贴板历史器，30s 自清空只是事后补救 |
| 决策 | **普通字段复制 30s 自清空；高敏感字段(密码/二级/支付/密钥) 默认不写系统剪贴板，走安全输入面板/受控复制** |
| 权衡 | ✅ 显著降低恶意读剪贴板风险；✅ 符合「最小暴露」原则；❌ 高敏感字段复制体验略降（需多一步受控操作） |
| 结论 | **采纳**（PRD §3.5.3，验收 8.5） |
| 后续 | 提供「用户可配置是否允许高敏感写剪贴板」的选项，但默认关闭 + 警告 |

## ADR-007｜抓取/AutoFill 权限：全量监听 vs 授权域白名单

| 项 | 内容 |
| :-- | :-- |
| 背景 | 跨应用/网页读输入权限与恶意软件同类，商店风控与隐私风险高 |
| 决策 | **默认关闭 + 授权域白名单 + 黑名单优先；权限逐项确认并明示信任边界** |
| 权衡 | ✅ 缩小暴露面，规避商店风控与合规风险；✅ 用户可控；❌ 首次使用需配置，牺牲一点自动化便捷 |
| 结论 | **采纳**（PRD §3.2，验收 8.4） |
| 后续 | 提供「一键从浏览记录导入常用站点到白名单」降低配置成本 |

## ADR-008｜内存安全：物理清零 vs 务实缓解

| 项 | 内容 |
| :-- | :-- |
| 背景 | PRD 提出「内存即擦除」，但托管语言无法可靠物理清零内存 |
| 决策 | **不承诺物理清零；改用『敏感值专用容器 + 完成置空引用 + 不复用字符串/避免日志』的务实缓解**，并在 UI 如实说明 |
| 权衡 | ✅ 不误导用户、不过度宣称；✅ 实现可行；❌ 无法完全防内存 dump（接受此局限） |
| 结论 | **采纳**（PRD §4 措辞已修订，验收 8.1） |
| 后续 | 评估 TEE（如 Android StrongBox / Secure Enclave）存储高敏感短生命周期数据 |

## ADR-009｜防录屏平台差异：FLAG_SECURE 仅 Android

| 项 | 内容 |
| :-- | :-- |
| 背景 | iOS 无 FLAG_SECURE 对等能力（属系统限制） |
| 决策 | **Android 用 FLAG_SECURE；iOS 用前台监听 + 越狱/证书检测等弱化方案，并在 UI 中如实告知能力差异** |
| 权衡 | ✅ 发挥各自平台最大防护；✅ 不虚假承诺；❌ iOS 防护弱于 Android，需用户知情 |
| 结论 | **采纳**（PRD §4/架构规格 §10.3） |
| 后续 | 关注 iOS 系统更新是否引入等效机制，适时增强 |

## ADR-010｜防爆破：指数退避锁定 + 绝不自动清空数据

| 项 | 内容 |
| :-- | :-- |
| 背景 | V1.0「输错 10 次清空缓存」属反模式（可被用于故意摧毁数据/DoS） |
| 决策 | **仅指数退避锁定(5m→…→30m上限)；绝无任何自动清空/删除；清除数据=主动+二次确认+确认短语** |
| 权衡 | ✅ 杜绝恶意摧毁与勒索向量；✅ 符合主流密码管理器实践；❌ 需设计「主动清除」的较强验证路径 |
| 结论 | **采纳**（PRD §3.4.3，验收 8.2 & 总纲第 0 条） |
| 后续 | 删除/清空流程需单独的确认短语 + 支持撤销/观察期（见 PRD §5） |

## ADR-011｜PC 原型数据库加密：应用层字段级加密（SQLCipher 延后）

| 项 | 内容 |
| :-- | :-- |
| 背景 | docs/04 原定 SQLCipher 做数据库级加密（密钥=DEK）。但当前开发环境为 rustc 1.75：SQLCipher 依赖的 `openssl-sys ≥0.9.117` 要求 rustc 1.80+，vendored OpenSSL 亦需更高工具链，无法构建。 |
| 决策 | **PC 原型阶段采用「应用层字段级 AES-256-GCM 加密 + bundled SQLite」**：所有敏感列（平台名/网址/账号/备注/各类密码）在写入前加密，DEK 永不入库。**SQLCipher 列为移动端生产加固项**，待工具链升级后启用（可用 feature flag 切换）。 |
| 权衡 | ✅ DB 文件被拷贝也读不到明文（安全性质等价达成，已有自动化断言）；✅ 无 OpenSSL 依赖，构建稳定；✅ 字段级加密本就是 FDEK 设计的一部分，非临时权宜；❌ 元数据（表结构、计数、`importance`/时间戳）未加密，弱于 SQLCipher 的全库加密。 |
| 结论 | **采纳（原型）**，生产目标仍为 SQLCipher；偏差已记录于 README「已知约束」。 |
| 后续 | T4.6 前评估：升级工具链后启用 `bundled-sqlcipher`，并补 `TC-CRY-01` 的 DB 级加密用例。 |

## ADR-012｜密码提示词以明文存储（功能决定）

| 项 | 内容 |
| :-- | :-- |
| 背景 | 提示词必须能在**主密码遗忘、库未解锁**时显示（否则提示词毫无意义）。而解锁前 DEK 不可用，任何用 DEK 加密的方案都无法在此时解密——这是先有鸡还是先有蛋的问题。 |
| 决策 | `meta.hint` **以明文存储**；UI 明确告知「解锁前可见，故明文保存」并在保存时二次确认；文档如实说明。 |
| 权衡 | ✅ 唯一能实现「锁定态可读」的方案；✅ 提示词按设计不含机密（仅记忆线索）；❌ 数据库文件被窃取时会泄露提示词内容。 |
| 结论 | **采纳**。威胁可接受（提示词非机密凭证），但必须：① UI 强警示；② 保存前二次确认；③ 禁止写入密码本身。 |
| 影响 | 「数据库无明文」的安全断言需精确表述为：**凭证字段（平台名/账号/备注/各类密码）全部加密；提示词按上述设计为明文**。 |
| 后续可选增强 | 将提示词改存系统凭据库（Keychain/Keystore）；或允许用户选择完全不设置提示词。 |
