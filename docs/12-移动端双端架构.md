# 12 · 移动端双端架构（ArkTS/NAPI + Android APK）

> 目标机：**华为 Mate 50 及后续鸿蒙机型**。
> 结论先行：由于 HarmonyOS 两代系统互不兼容，**必须双端开发**
> （Android APK 覆盖 HarmonyOS 3/4 存量 + HarmonyOS NEXT 原生 HAP 覆盖 NEXT）。
> 你的 **Rust 核心 + C ABI** 恰好让双端只剩 UI 需双写，业务逻辑零重写。

---

## 0. 决策摘要

| 维度 | 结论 |
| :-- | :-- |
| Mate 50 当前系统 | HarmonyOS 3.x/4.x（AOSP 兼容层）→ **只能装 Android APK** |
| Mate 50 升级 NEXT 后 | HarmonyOS NEXT 5.x（无 AOSP）→ **只能装原生 HAP** |
| **结论** | **双端开发**：APK + NEXT 原生 |
| Rust 核心 | **零改动复用**（`vault_ffi` 11 个 C ABI 符号，已 Miri 验证 + 鸿蒙交叉编译 PoC 通过） |
| UI 层 | 双写：Android (Kotlin + JNI) 与 NEXT (ArkTS + ohos-rs/NAPI) |
| 工作量 | 双端 ≈ 单端 Android 的 **1.3–1.6 倍**（核心共享摊薄） |

---

## 1. 为什么必须双端（Mate 50 兼容性结论）

调研（2026-10）确认两代系统**刻意互不兼容**：

| | HarmonyOS 3/4（兼容版） | HarmonyOS NEXT 5.x（纯血） |
| :-- | :-- | :-- |
| 内核 | AOSP + 双框架 | OpenHarmony，无 AOSP |
| 应用格式 | APK（+ 旧 FA 模型） | HAP（Stage 模型 + ArkTS） |
| 装 APK | ✅ | ❌（`INSTALL_FAILED_INVALID_APK`，且升级即清空已装 APK） |
| 装 NEXT 原生 HAP | ❌ | ✅ |

- **Mate 50 可升级 NEXT**：已分批纳入（2026 年 OTA 4.2→5.0），但属**后续批次**，最高约 **API 12–14**（NEXT 5.0 早期 build）。
- ⚠️ **不能假设用户已升级**：升级是分批灰度，且一旦升 NEXT 就永久失去 APK 能力，很多用户刻意留在 4.2。现实中"双轨并存"是常态。
- **结论**：单做 APK 会在用户升 NEXT 后失效；单做 NEXT 原生则**装不上**当前 3/4 的 Mate 50。**必须双端**。

---

## 2. 总体架构

```
                 ┌─────────────── 共享 Rust 核心（C ABI）───────────────┐
                 │  security_core │ vault_store │ 业务逻辑（零改动）      │
                 │  Argon2id/AES-GCM │ SQLite(bundled) │ 找回/备份/审计   │
                 └────────┬────────────────────────────────┬────────────┘
                          │ C ABI（vault_ffi: 11 符号）       │ C ABI
                          ▼                                 ▼
        ┌───────────────────────┐            ┌─────────────────────────┐
        │  Android App（APK）    │            │  HarmonyOS Next（HAP）   │
        │  语言: Kotlin          │            │  语言: ArkTS / ArkUI    │
        │  桥接: JNI             │            │  桥接: ohos-rs (NAPI)   │
        │  密钥库: Android Keystore│           │  密钥库: HUKS            │
        │  防截图: FLAG_SECURE   │            │  防截图: 窗口防截屏       │
        └───────────────────────┘            └─────────────────────────┘
```

**关键设计原则**：所有加密、存储、业务逻辑都在 Rust；App 只是**薄壳 + UI + 平台能力**（生/指纹、密钥库、防截图、剪贴板）。

---

## 3. NEXT 端（ArkTS/NAPI）—— 你点名要的壳层

### 3.1 桥接路线：`ohos-rs`（napi-rs 的鸿蒙 fork）

| 项 | 说明 |
| :-- | :-- |
| 工具 | `ohos-rs`（`cargo install ohrs` + `cargo add napi-ohos napi-derive-ohos`） |
| 产出 | 自动生成 ArkTS/TS 声明 + `.so` |
| 兼容基线 | **API 12**（恰好匹配 Mate 50 可达到的最低 NEXT build）✅ |
| 成熟度 | 1.0.0（2024-10），多款上架应用，对齐 napi-rs 测试集 |
| 注意 | 鸿蒙 N-API 有差异（不支持 Symbol 相关、空 buffer 等）；**单测强依赖真机** |

### 3.2 Rust 核心 → NAPI 包装

两种做法：
- **直接包装 vault_ffi 的 11 个 C 符号**（现成，Miri 已验）—— 用 `#[napi]` 薄包一层 ArkTS 可调函数；
- 或改用 `#[napi]` 重写桥接（更顺，但需保证与 jail_ffi 等价）。

推荐先做**前者**（复用已验证的 FFI，零风险），后续再视需要迁移。

### 3.3 NEXT 平台能力（HUAWEI 官方提供）

| 需求 | NEXT 等价物 | 状态 |
| :-- | :-- | :-- |
| 硬件密钥库 | **Universal Keystore Kit (HUKS)** | ✅ AES/RSA/ECC/ED25519; TEE；支持 PIN/生物绑定 |
| 生物识别 | User Authentication Kit | ✅ 指纹/人脸；新录生物特征即失效 |
| 防截图 | 窗口级防截屏 API | ✅ |
| 剪贴板 | 系统剪贴板 API | ✅ |

> ⚠️ **设计注意**：FuxiPass 目前 DEK 由主密码经 Argon2 派生包裹，主密码是唯一门禁。
> 若要"生物一键解锁"，需**新增一条 HUKS 包裹路径**（存 HUKS 封装的密钥来解 FDEK）—— 属新增工作，非阻塞。

## 4. Android 端（APK）

| 项 | 说明 |
| :-- | :-- |
| 语言/UI | Kotlin + Jetpack Compose（或传统 View） |
| 桥接 | **JNI** 调 `vault_ffi.so`（rust 产物 `libvault_ffi.so`） |
| 密钥库 | Android Keystore（等价 HUKS） |
| 防截图 | `FLAG_SECURE` |
| 侧载 | **开放**（AppGallery 或任意来源）→ 3/4 设备更新友好 |

---

## 5. 签名 / 分发通道（对"确保能装"至关重要）

| 通道 | Android APK | NEXT HAP |
| :-- | :-- | :-- |
| 侧载 | ✅ 开放 | ❌ **受限**：仅 debug profile（UDID 白名单）/企业包（绑设备） |
| 正式分发 | AppGallery / 各商店 | **必须 AppGallery 上架**（企业/个人实名认证） |
| 真机调试 | adb，无门槛 | DevEco + 真机 UDID 注册 |

> **实际影响**：NEXT 侧想给**大众用户**普及，几乎只能走 **AppGallery 上架 + 企业认证**；
> 指望 `hdc install` 侧载给任意用户不可行。
> 这与密码管理器的"低门槛分发"诉求有张力 → 建议早期以**自己和测试机**为主，上架再议。

## 6. 工作量与风险

### 6.1 工作量估算（人天）

| 模块 | Android | NEXT | 说明 |
| :-- | :-- | :-- | :-- |
| Rust 桥接层 | 2–3 | 2–3 | 复用 vault_ffi，薄包装 |
| UI 壳（列表/详情/新增/设置） | 8–12 | 8–12 | 双写 |
| 生物解锁 / 密钥库接入 | 2–3 | 2–3 | HUKS / Keystore |
| 防截图 / 剪贴板 | 1–2 | 1–2 | 各有等价物 |
| 签名 / 上架 / 真机 | 2–3 | 3–5 | NEXT 更繁琐 |
| **合计** | **15–23** | **16–25** | 双端并行 ≈ 1.3–1.6× 单端 |

### 6.2 风险

| 风险 | 等级 | 缓解 |
| :-- | :-- | :-- |
| 用户是否已升 NEXT（影响 APK 覆盖率） | 🟡 | 双端并行，覆盖全部 |
| NEXT 真机 / 模拟器获取（海外/非认证账号申请白名单） | 🟡 | 中国区低摩擦；先备真机 |
| **Miri 在 OHOS 目标不可用**（官方限制） | 🟢 | 作为 FFI 内存安全保障的损失，需靠 Android/本机 Miri + REVIEW 弥补 |
| ohos-rs 生态较新、单测依赖真机 | 🟢 | 先做最小 PoC 上真机 |
| NEXT 侧载受限 → 分发渠道 | 🟡 | 上架 AppGallery + 企业认证 |
